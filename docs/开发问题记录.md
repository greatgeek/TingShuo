## 1. 环境与工具（Windows）

### P-001 全局 git 代理（ghfast.top）导致 push 认证失败 · 2026-10-26

- **现象**：`git clone` 成功，但 `git push` 报 `remote: Invalid username or token ... Authentication failed for 'https://ghfast.top/https://github.com/...'`
- **根因**：全局配置 `url.https://ghfast.top/https://github.com/.insteadOf` 把所有 GitHub 请求重写到只读加速镜像，且 `git clone` 会把重写后的 URL 固化进新仓库的 `origin`
- **解决**：`git config --global --unset-all url.<代理>.insteadOf` + `git remote set-url origin https://github.com/greatgeek/TingShuo.git`
- **备注**：加速器只读（fetch 可用、push 不行）；判断依据是报错 URL 带 `ghfast.top` 前缀

### P-002 无交互 shell 环境的 GitHub 认证 · 2026-10-26

- **现象**：AI 助手环境执行 `git push` 报 `could not read Username for 'https://github.com'`（GCM 凭据弹窗无法完成）
- **根因**：执行环境无交互终端，GCM 的 GUI 认证流程走不通
- **解决**：用户在自己终端手动 `git push -u origin main` 完成一次浏览器 OAuth 登录，凭据进入 Windows 凭据管理器后，此后任何环境 `git push` 直接可用

### P-003 agent-browser 的 Chromium 默认落 C 盘 · 2026-10-26

- **现象**：`agent-browser install` 把 199MB Chrome 装到 `C:\Users\<user>\.agent-browser\`，不读 `PLAYWRIGHT_BROWSERS_PATH`
- **解决**：目录整体 `robocopy /MOVE` 到 `G:\TingShuo\agent-browser`，在原路径建 `mklink /J` junction，agent-browser 无感知
- **约定**：本机所有软件/数据一律装 G 盘（用户要求），C 盘仅允许 junction 链接

### P-004 PowerShell 处理 UTF-8 请求/响应的两个坑 · 2026-10-26

- **现象 1**：API 响应的日语显示为 `??????`——`Invoke-RestMethod` 按 GBK 解码 UTF-8
- **解决 1**：改用 `curl.exe -o <file>` 落盘，再 `[IO.File]::ReadAllText(path, UTF8)` 读
- **现象 2**：POST JSON 报 `invalid char "\ufeff{"`——`Out-File -Encoding utf8` 在 Windows PowerShell 写入 BOM 头
- **解决 2**：用 `[IO.File]::WriteAllText(path, json, (New-Object Text.UTF8Encoding($false)))` 写无 BOM 文件
- **规避**：这正是部署文档 §5「任务脚本一律 Go 程序」的价值——跨平台调 API 一律写 Go（`cmd/smoke`），不再手搓 PowerShell

### P-005 `cmd /c` 吞掉同行的 PowerShell 语句 · 2026-10-26

- **现象**：`cmd /c mklink ...; Get-ChildItem ...` 报 `'Select-Object' 不是内部或外部命令`
- **根因**：`;` 分隔的后续 PowerShell 语句被当成 `cmd /c` 的参数，进入 cmd 上下文执行
- **解决**：`cmd /c` 只单独执行其自身参数，不与 PowerShell cmdlet 混写同行

### P-006 agent-browser 要求 Node ≥ 24（本机 20.11.1）· 2026-10-26

- **现象**：`npm i -g agent-browser` 报 `EBADENGINE Unsupported engine { node: '>=24.0.0' }`
- **现状**：仅为警告，实测可正常启动与操作浏览器
- **预案**：若后续 daemon 崩溃/行为异常，用 `install_binary` 安装 Node 24 后重装

## 2. 依赖与服务

### P-007 MinIO 开源版已归档，官方下载全线 410 · 2026-10-26

- **现象**：`dl.min.io/server/minio/release/...` 与 `.../archive/...` 均返回 `410 Gone`（"open-source MinIO Server is archived and no longer maintained"）；GitHub releases 从不提供二进制；npmmirror 无镜像
- **根因**：MinIO 2025-04 宣布开源 server 归档、撤下分发
- **解决**：本地对象存储改用 **RustFS 1.0.4**（`G:\TingShuo\rustfs\rustfs.exe`，S3 API 兼容、预签名 URL 同语义）
- **影响**：生产环境不受影响（走阿里云 OSS）；本地开发的 S3 交互（PutObject/GetObject/Presigned PUT）与 MinIO 完全一致
- **待验证**：RustFS 预签名 URL 与 Go S3 SDK 的互操作（M1 集成测试覆盖，见 Q-003）

### P-008 RustFS 启动即退：数据目录必须预先创建 · 2026-10-26

- **现象**：`Start-Process rustfs.exe server <dir>` 进程秒退，端口无监听
- **根因**：数据目录不存在时 RustFS 不会自动创建（MinIO 会），且 `Start-Process` 默认吞掉 stderr 看不到报错
- **解决**：先 `New-Item -ItemType Directory` 再启动；启动命令带 `-RedirectStandardError` 落日志便于诊断

### P-009 PG zip 解压被切后台导致 initdb 失败 · 2026-10-26

- **现象**：`initdb` 报 `file ".../share/postgres.bki" does not exist`
- **根因**：EDB binaries zip 解压耗时较长且在后台执行，`bin` 先就位而 `share` 尚未解完，过早执行 initdb
- **解决**：确认 `share` 目录文件数齐全后重跑 initdb 即成功；后续可等待解压进程退出再初始化

### P-010 Go 版本与 GOPROXY · 2026-10-26

- **现象**：本机 Go 1.20.4，文档要求 1.22+；默认 GOPROXY（proxy.golang.org）国内不可达
- **解决**：`go env -w GOPROXY=https://goproxy.cn,direct`；当前代码全部兼容 1.20（依赖锁定 pgx v5.5.5）
- **约定**：写代码避开 1.21+ 特性（如 `log/slog`）；若必须升级再评估

### P-011 PostgreSQL 免安装版部署要点（Windows）· 2026-10-26

- 路径：`G:\TingShuo\pgsql`（binaries）+ `G:\TingShuo\pgdata`（数据目录）
- 初始化：`initdb -U tingshuo -E UTF8 --no-locale -D G:\TingShuo\pgdata -A trust`（本地 trust 认证、C locale 避免 GBK 坑）
- 启动：`pg_ctl -D G:\TingShuo\pgdata -l <logfile> start`；注意服务非开机自启，重启机器后需手动启动

### P-018 Go 1.20.4 → 1.24.10 升级实录 · 2026-10-26

- **诱因**：chi v5.5.0 使用 Go 1.21+ 标准库 `slices`，Go 1.20 编译失败；文档要求 Go 1.22+，开发机落后
- **下载**：阿里云镜像 `https://mirrors.aliyun.com/golang/go1.24.10.windows-amd64.zip`
- **坑 1**：原 GOROOT 目录 `G:\GoLang` Rename 被系统拒绝（非 gopls 占用、非 ACL，疑似 IDE/安全软件目录句柄；gopls 已杀仍拒绝）
- **解决**：新 Go 解压至 `G:\TingShuo\go1.24\go`（不动旧目录），用户级 `GOROOT` 指向新路径 + 用户 PATH 前插新 `bin`；机器级 GOROOT 未动（用户级覆盖机器级）
- **坑 2**：IDE 已运行进程感知不到环境变量变更——子 shell 继承旧 `GOROOT=G:\GoLang`，导致新 go 用旧标准库（`compile version mismatch`）。IDE 重启前每条命令需显式 `$env:GOROOT="G:\TingShuo\go1.24\go"`
- **教训**：Go 1.5+ 本不需要 GOROOT 环境变量（自动推导），残留的旧 GOROOT 反而是事故源

### P-019 Go 1.24 的 GOSUMDB 校验 · 2026-10-26

- **现象**：`go mod tidy` 报 `verifying go.mod: missing GOSUMDB`
- **根因**：Go 1.24 依赖 sumdb 校验（sum.golang.org 国内不通），本机未配置
- **解决**：`go env -w GOSUMDB="sum.golang.org https://goproxy.cn/sumdb/sum.golang.org"`（走 goproxy.cn 镜像校验，保留供应链完整性检查）

### P-020 Expand-Archive 静默失败，tar 更可靠 · 2026-10-26

- **现象**：`Expand-Archive -Force` 无报错但目标目录为空
- **解决**：改用系统自带 bsdtar：`tar -xf <zip> -C <dest>`，一次成功
- **约定**：本机解压一律优先 `tar`（Windows 10+ 自带，支持 zip/tar.gz）

## 3. Azure TTS 排查实录（重要）

### P-012 Key 手抄一字之差 → 两个 Key 全部 401 · 2026-10-26

- **现象**：KEY 1/KEY 2 调用 TTS 全部 401；换区域（7 个）、换认证头（Ocp-Apim / Bearer）、换 Key 均无效
- **根因**：用户肉眼手抄 84 位密钥，第 62 位 `B` 抄成 `W`（`ACqBBLy` → `ACqWBLy`）——Azure 逐字符校验，一字之差整把无效
- **教训**：长密钥一律点页面**复制图标**，禁止手打；排查时先做「长度 + 首尾 + 与页面逐段 diff」比对

### P-013 新版语音资源不挂统一端点，必须用专用域名 · 2026-10-26

- **现象**：Portal「密钥和终结点」显示统一终结点 `https://southeastasia.api.cognitive.microsoft.com/`，但对该域名 POST `/cognitiveservices/v1` 与 `/sts/v1/issueToken` 恒 404 `Resource not found`
- **根因**：微软正把认知服务从统一 API 域名迁移到功能专用域名（TTS：`tts.speech.microsoft.com`、STT：`stt.speech.microsoft.com`）；2024+ 新建的语音资源已不在统一域名上挂 TTS，Portal 显示文案滞后
- **解决**：TTS REST 调用统一走 `https://{region}.tts.speech.microsoft.com/cognitiveservices/v1`
- **架构决策**：`ttsclient` 按区域拼装专用域名；客户端设置仅暴露 Key + Region 两个值（FR-10.8），终结点由代码生成，用户不接触此坑

### P-014 `*.cognitiveservices.azure.com` DNS 泛解析干扰排查 · 2026-10-26

- **现象**：`Resolve-DnsName tingshuo.cognitiveservices.azure.com` 显示"存在"，但 curl 请求 HTTP 000（TLS 握手失败）
- **根因**：该域是泛解析，任意子域都有 DNS 记录；真实存在与否取决于 Azure 前端有无证书与配置
- **教训**：判定子域是否有效用「实际 HTTPS 请求」而非 DNS 解析；000/TLS 失败 = 不存在，404/401 = 域名存在但资源/认证问题

## 4. 代码与测试（M0）

### P-015 迁移工具 CREATE TABLE 语句缺右括号 · 2026-10-26

- **现象**：`migrate up` 报 `syntax error at end of input (SQLSTATE 42601)`
- **根因**：Go raw string 里 SQL 少写一个 `)`；simple protocol 下错误信息不带行号，不易定位
- **改进**：迁移文件执行失败时打印文件名与语句片段（M1 完善错误上下文）

### P-016 ULID `Time()` 只校验前 10 位字符 · 2026-10-26

- **现象**：单测构造「非法字符在末尾」的 26 位 ID，解析未报错
- **根因**：实现只遍历前 10 位（时间戳段），后 16 位不校验
- **解决**：改为全 26 位合法性校验、仅前 10 位参与时间累积；作为 ID 校验器更严谨（同步游标依赖）

### P-017 测试用例自身设计失误（cachekey 空白归一化）· 2026-10-26

- **现象**：`TestCacheKeyNormalizesWhitespace` 失败
- **根因**：两个测试输入并非「仅空白差异」（一个句中有空格、一个没有），断言预期错误
- **教训**：失败时先审测试用例自身是否成立，再查实现

## 5. 待决事项与文档矛盾

### Q-001 复习首次间隔口径：AC-7.1 与 §8.5 矛盾

- AC-7.1：标记难点后首次复习出现在 **D+2**（推得首次 interval=2）
- §8.5 代码注释：**首次入池 interval=1**（due = D+1）
- **现状**：`internal/review/schedule.go` 按 §8.5 实现（首次 1 天），代码注释已标记差异
- **裁决计划**：M3 复习页集成测试时按实际体验定稿，回头修订文档统一口径

### Q-002 `word` 表 UNIQUE(user_id, surface, reading) 中 reading 为 NULL

- PG 默认 NULL 互不相等：同词无读音可重复入库，违反词去重意图（FR-1.5）
- **候选方案**：a) 应用层先补全读音；b) 升级为 `UNIQUE NULLS NOT DISTINCT`（PG15+）
- **裁决计划**：M1 词单解析器落地时一并决定

### Q-003 RustFS 预签名 URL 与 Go S3 SDK 的互操作

- RustFS 为 MinIO 替代品，S3 语义兼容性靠 M1 的 storage 层集成测试验证（PutObject/Presigned PUT/Presigned GET）
- 若预签名行为有差异，备选：SeaweedFS 或本地 MinIO 历史版本（如社区留存的最后开源版）
- **验证载体**：M1 的 `cmd/smoke`（对象上传/下载段落）
